## SpinDeckは何をするもの？

SpinDeckは、**サーバーの中身（Kubernetesやコマンドライン）を一切触らずに、
ブラウザだけでアプリを公開できるWebコンソール**です。

- コードをブラウザ内のエディタに貼り付けるだけで、アプリが自動的にビルド・
  デプロイされ、`https://あなたのドメイン/アプリ名/` のようなURLで公開されます。
- 「JavaScriptのコード」「HTML/CSS/JS（+ PHP）の静的サイト」「別サーバーへの
  中継（リバースプロキシ）」「定期実行するPython/bashスクリプト」
  「任意のDockerイメージ」の5種類のアプリが作れます。
- パスワード保護や、社内のログイン基盤（Keycloak）を使った認証も、画面から
  設定するだけで有効にできます。コンソール自体のログインも、Keycloakの
  代わりにコンソール内蔵のユーザー名/パスワード認証を選ぶこともできます。
- 裏側では、届いたアプリのコードを [SpinKube](https://www.spinkube.dev/)
  という仕組み（WebAssembly / Wasmという軽量な実行形式でアプリを動かす、
  Kubernetesの拡張）でビルド・実行しています。この部分の詳細を知らなくても
  SpinDeckは使えます。

要するに、「ちょっとしたAPIやサイトを作って、すぐ公開したい」というときに、
インフラの知識がなくても使える社内PaaS（Platform as a Service）です。

## 基本の考え方

SpinDeckを使う上で知っておくと良い、3つの考え方があります。

### 1. 「アプリ」は5種類ある

| 種類 | 何ができる？ | こんなときに使う |
| --- | --- | --- |
| **New App** | JavaScriptのコードを動かす | ちょっとしたAPI、Webhook受け口、Cloudflare Workers風の処理 |
| **New Site** | HTML/CSS/JS（+ PHP）のファイル一式を公開する | 静的サイト、簡単な社内ツールのフロントエンド |
| **New Proxy** | 別のサーバーへリクエストを中継する | 既に動いている社内システムに、SpinDeck経由でアクセスさせたいとき |
| **New Cron** | Python/bashのスクリプトを定期実行する | 毎朝のバッチ処理、定期メール送信、外部APIのポーリング |
| **New Container** | 任意のDockerイメージをそのまま動かす | 公開されているDockerイメージをそのまま使いたい、他の種類では表現できない構成が必要なとき |

New App/Site/Proxy/CronはSpinKube（WebAssembly）の上で動きますが、
New Containerだけは通常のDockerコンテナとしてそのまま動きます（詳細は
[New Container（Dockerコンテナ）](#new-containerdockerコンテナ)を参照）。

### 2. アプリの公開のされ方

New App/Site/Proxy/Cronは、`https://<公開ホスト名>/<アプリ名>/` という
1つのURLの下にぶら下がって公開されます。例えば公開ホスト名が
`apps.example.com` で、アプリ名が `hello` なら、
`https://apps.example.com/hello/` です。この「公開ホスト名」は `/config`
ページで設定・変更できます（後述）。必要であれば、アプリごとに
「専用ドメイン」を割り当てることもできます
（[独自ドメイン（FQDN）で公開する](#独自ドメインfqdnで公開する)を参照）。

New Containerは少し異なり、専用ドメインを1つ丸ごと占有する形で公開されます
（パスの下にはぶら下がりません）。専用ドメインを指定しなければ、外部には
一切公開されない「計算専用」のコンテナとしても使えます（詳細は
[New Container（Dockerコンテナ）](#new-containerdockerコンテナ)を参照）。

### 3. 変更はすぐ反映される

「保存」を押すと、コードのビルドとデプロイが自動的に走り、数秒〜十数秒で
反映されます。サーバーを再起動したり、手動でデプロイコマンドを打つ必要は
ありません。

## 初めてログインする

コンソールのログイン方式は、管理者が`/config`で「Keycloak（OIDC）」か
「ローカルアカウント」のどちらかを選んでいます（詳細は
[コンソール自体を守る](#コンソール自体を守るログイン方式アクセス制限)を
参照）。どちらの方式でも、最初の使い方は同じです。

1. ブラウザで SpinDeck のURL（インストール直後は `http://<サーバーのIP>:8080/`、
   運用が進んで独自ドメインが設定されていれば `https://<ドメイン>/`）を開きます。
2. **Keycloakの場合**: 自動的にKeycloak（社内のログイン基盤）のログイン画面へ
   リダイレクトされます。普段お使いのアカウントでログインしてください。
   **ローカルアカウントの場合**: SpinDeck自身のログインフォームが表示されます。
   管理者から発行されたユーザー名/パスワードを入力してください。
3. ログインすると、ダッシュボードが表示されます。上部の「システム状態」
   カードには、このノードのホスト名・OS・稼働時間・CPU負荷（load
   average）・メモリ使用量・k3s/cert-manager/SpinKube operator/Traefikの
   バージョンが表示されます（cert-manager以降の3つは`upgrade.sh`実行時に
   記録されるため、一度も実行していないインストールでは「—」表示に
   なります）。その下に登録済みのアプリ一覧が続きます。最初は何も
   登録されていないはずです。

> ログインできない・エラーになる場合は、インストールを行った管理者に
> 確認してもらってください（Keycloakの場合は`/etc/spinapp-ui/env`の
> `SPINAPP_UI_OIDC_*`、ローカルアカウントの場合はユーザー名/パスワードが
> `/config`の「ローカルアカウント管理」に登録されているか）。

## アプリを作ってみる

### New App（JavaScript）

一番手軽にAPIやWebhookを作れる方法です。

1. 上部ナビゲーションの **➕ New App** を開きます。
2. アプリ名（英小文字・数字・ハイフンのみ、例: `hello-api`）を入力します。
3. エディタにJavaScriptのコードを書きます。最初から用意されているサンプル
   コードを少し書き換えるだけでも動作を確認できます。
   [Cloudflare Workers](https://developers.cloudflare.com/workers/) と
   似たスタイル（`addEventListener('fetch', ...)` や
   `export default { fetch(request) { ... } }`）で書けます。
4. **プレビュー**タブでブラウザ内から動作確認ができます（デプロイ前は404に
   なるので、まず保存してください）。
5. 「Build & Deploy」を押すと、コードがWasmにビルドされ、自動的に
   `https://<公開ホスト名>/<アプリ名>/` で公開されます。

> 外部のAPIを呼び出すコード（`fetch()`）も、特別な設定なしにそのまま動作
> します。ただしその分、公開範囲には注意してください（後述の
> [アプリを守る（認証）](#アプリを守る認証)を参照）。

### New Site（静的サイト・PHP）

ビルド不要で、HTML/CSS/JSファイルをそのまま公開したいときに使います。

1. **🌐 New Site** を開きます。
2. アプリ名を入力し、ファイルを追加していきます（`index.html` は必須、
   サブディレクトリも作れます）。
3. 画像・PDFなどのバイナリファイルもアップロードできます。
4. `.php` ファイルを含めると、自動的にPHPが動く構成に切り替わります
   （追加設定は不要です）。
5. 「Build & Deploy」で公開されます。

### New Proxy（リバースプロキシ）

既に社内で動いている別のシステム（例: 社内ツール、別サーバーのWebアプリ）を、
SpinDeck経由で公開・中継したいときに使います。

1. **🔀 New Proxy** を開きます。
2. アプリ名と、転送先の **Backend Origin**（例:
   `http://10.0.0.50:8080`）を入力します。パスを付けて入力すると
   （例: `http://10.0.0.50:8080/app`）、転送先が特定のサブパスでの
   アクセスを前提にしている場合にも対応できます。
3. 必要に応じて、パスごとの挙動（そのまま転送する／404にする／別パスの
   内容に差し替える）をルールとして追加できます。
4. サブパス配信でレスポンス中のURLを書き換えたい場合は、「書き換えルール」
   （上級者向け）を使います。

> **セキュリティ上の注意**: Backend Originにクラウドのメタデータ
> アドレスや、明らかに内部専用のアドレス（例: Kubernetesクラスタの内部
> IP）を指定することはできません（保存時にエラーになります）。ただし、
> これは入力ミスを防ぐための簡易チェックであり、完全な防御ではありません
> — 信頼できる担当者だけがこの機能を使えるようにしてください。

### New Cron（定期実行ジョブ）

Python または bash のスクリプトを、cronのスケジュールで定期実行できます。

1. **⏰ New Cron** を開きます。
2. アプリ名、実行スケジュール（cron形式、例: `0 9 * * *` で毎日9時）、
   実行するコードを入力します。
3. メールを送りたい場合は `send_mail(宛先, 件名, 本文)` が、bashで
   URLを取得したい場合は `download(url, 保存先, [User-Agent])` が、
   それぞれ追加設定なしで使えます。
4. 過去の実行結果は編集画面の「実行ログ」タブから確認できます。

### New Container（Dockerコンテナ）

任意のDockerイメージを、Wasmサンドボックスを介さない通常のコンテナ
（Kubernetesの`Deployment`）としてそのまま実行します。公開されている
Dockerイメージ（nginx、postgresなど）をそのまま動かしたいときや、
他の種類のアプリでは表現しきれない構成が必要なときに使います。

> **信頼できるイメージのみを指定してください。** 他の種類（Wasmサンドボックス
> 内で動作）と違い、指定したイメージはroot権限で動作する可能性があります。
> 既定では認証不要の公開イメージ（Docker Hub / GHCRなど）のみ指定できますが、
> `/config`の「New Container 用レジストリ認証」に登録したホストについては
> ログイン情報を使ってpullできます（例: 自前の非公開レジストリ）。

1. **📦 New Container** を開きます。
2. アプリ名とイメージ（例: `nginx:latest`）を入力します。**起動コマンド**は
   任意です。素の`python`・`node`等は既定のコマンドがすぐ終了して
   再起動を繰り返すため、その場合は`sleep infinity`のような起動し続ける
   コマンドを指定してください（チェックボックスで自動入力できます）。
   **環境変数**も`KEY=VALUE`を1行に1つの形式で指定できます。
3. **CPU上限**・**メモリ上限**（例: `500m`・`512Mi`）、**レプリカ数**
   （2以上にすると、Kubernetesの`Service`が自動的にラウンドロビンで
   負荷分散します）を設定します。メモリは指定した量を予約・上限とも
   確保します（他のアプリと取り合いにならない代わりに、空きがなければ
   デプロイ自体ができません）。CPUは上限のみで、実際の予約
   （スケジューラが確保する量）は常に少量の固定値です — 複数アプリで
   CPUをオーバーコミットできる代わりに、ノードのCPUが混み合っている
   時は指定した上限まで出ないことがあります。
4. **永続ストレージを使う**にチェックが入っていると、永続データが
   コンテナ内にマウントされます（既定は`/data`ですが、「マウント先パス」
   で変更できます — 例えばMySQL/MariaDBなら`/var/lib/mysql`のように、
   **そのイメージが実際にデータを書き込むパス**を指定してください。
   `/data`のままだと動いているように見えても実際には永続化されない
   イメージがあります）。ホスト側の実体は`/data/containers/<アプリ名>/`
   です（容量の上限はありません。ノードのディスク容量に依存します）。
   チェックを外すと、そのコンテナは永続化なし（Pod再作成のたびにデータが
   消える）になります。レプリカ数を2以上にする場合、全レプリカが
   同じ永続データを同時にマウントするため、同時書き込みに対応していない
   アプリ（多くのDBやシングルインスタンス前提のアプリ）はレプリカ数を
   1のままにしてください。
5. **専用ドメイン（FQDN）**と**ポート**は両方とも任意です。指定すると、
   そのアプリはFQDN全体を専有します（他の種類のようにパスの下には
   ぶら下がりません）。自由に入力できますが、他のアプリ（種類問わず）が
   既に使っているFQDNは指定できません。**空欄のままにすると、この
   ポート・TLSの扱い(Traefik経由の443番)による外部公開はなくなります**
   （ポート/Serviceも作成されません）、下記の🖥️コンソールタブからの
   操作専用のコンテナになります（計算処理専用の用途などに）。FQDNを
   指定する場合のみ、ポートの入力も必要です。後述の「追加の公開ポート」
   はFQDN/ポートの設定と関係なく使えるため、Traefik経由の443番公開は
   不要でVPNのような別ポートだけ公開したい場合は、ここを空欄にしたまま
   「追加の公開ポート」だけを設定できます。
6. FQDNを指定した場合、**TLSの扱い**を選べます:
   - **kubespin（Traefik）で終端**（推奨） — 他のアプリと同じく`/config`の
     HTTP/HTTPS設定にそのまま従います。Basic/OIDC認証やアクセスログ分析も
     このモードでのみ利用できます。
   - **コンテナへパススルー** — サイト全体の設定に関わらず常に443番
     ポートで待ち受け、TraefikはTLSを復号せず生データをそのまま
     コンテナへ転送します。コンテナ自身が証明書を用意して自分でHTTPSを
     終端する必要があります。
7. 「終端」モードでは、**「混在コンテンツを自動修正する」**も選べます。
   コンテナ自身が生成するHTMLに古い`http://`絶対URL（CSS/JS/画像など）が
   残っていて、HTTPSページ上でブラウザにブロックされてしまう場合の
   応急処置です（ブラウザに`http://`のサブリソース要求を自動的に
   `https://`へ書き換えさせるレスポンスヘッダーを追加します）。根本的には
   アプリ側の設定を`https://`に直すのが望ましいですが、すぐに直せない
   レガシーなアプリ（HTTPからHTTPSに切り替えた古いWordPress等）向けの
   回避策です。
8. 「Deploy」で公開されます。

編集画面の「Update & Redeploy」は、フォームの内容を1つも変えていなくても
**必ずPodを作り直します**。同じイメージタグに新しい内容をpushし直した
場合など、SpinDeck側からは変更を検知できないケースでも、「Update &
Redeploy」を押せば確実に新しいPodが作られ、最新のイメージがpullされます
（`imagePullPolicy`はイメージタグの既定挙動に従うため、`latest`以外の
固定タグではpull自体は再実行されず、ノードにキャッシュ済みのイメージが
そのまま使われる点に注意してください — 内容を確実に更新したい場合は
`latest`タグを使うか、タグ自体を変えてデプロイしてください）。
Containerアプリは更新のたびに、**古いPodを先に停止してから新しいPodを
作ります**（Kubernetesの既定のローリングアップデートではなく、常に
一旦停止してから作り直す方式です）。そのため、更新中は必ず一時的に
アクセスできなくなりますが、その代わり新旧2つ分のCPU/メモリが同時に
必要になることはありません（ノードのリソースが逼迫していても、確実に
Podを作り直せます）。

#### サイドカーコンテナ（複数コンテナの連携、例: WordPress + MySQL）

WordPressのように「連携する複数コンテナ」を1つのアプリとしてデプロイ
したい場合、「設定」タブの「サイドカーコンテナ」セクションから、同じPod内で
一緒に動く追加のコンテナを追加できます。

> **なぜ2つの別々のアプリではなく1つのPodにまとめるのか**: SpinDeckは
> セルフサービスで動くコードが内部ネットワークを踏み台にしないよう、
> 全アプリのPodに「クラスタ内の他のPod/Serviceへは通信できない」という
> 制限をかけています。そのため、New Containerを2つ別々に作っても
> 互いに通信できません。同じPod内のコンテナ同士は`localhost`で通信
> できるため、この制限を受けずに連携できます。

- メインのコンテナ（例: `wordpress:latest`）は通常通りイメージ・環境変数
  ・ポート等を設定します。永続ストレージは「永続ストレージを使う」で
  オン/オフでき、「マウント先パス」（既定`/data`）も変更できます。
- 「+ サイドカーコンテナを追加」で、連携させたいコンテナ（例:
  `mysql:8`）のイメージ・起動コマンド・環境変数・CPU/メモリ上限を設定します。
  最大6個まで追加できます（メインと合わせて1つのPodに最大7コンテナ）。
- メインのコンテナからは `127.0.0.1:<ポート番号>` でサイドカーへ接続できます
  （例: `WORDPRESS_DB_HOST=127.0.0.1:3306`）。
- 永続化が必要な場合（データベースなど）は「永続ストレージを使う」に
  チェックし、**そのイメージが実際にデータを書き込むパス**を「マウント先
  パス」に入力してください（例: MySQL/MariaDBなら`/var/lib/mysql`、
  PostgreSQLなら`/var/lib/postgresql/data`）。空欄のままだと`/data`に
  なりますが、多くのデータベースイメージは`/data`ではなく自分専用の
  パスにデータを書き込むため、**イメージに合わせて正しいパスを指定
  しないと、見た目上は動いていても実際には永続化されず、Pod再作成時に
  データが消えてしまいます**。メインコンテナ・各サイドカーはそれぞれ
  別の専用ディレクトリを自動的に使うため、データが混ざる心配はありません。
- **レプリカ数は1のままにしてください** — 2以上にするとサイドカーも
  レプリカごとに個別に立ち上がってしまい、データベース等は正しく
  共有されません。
- 🖥️コンソール（ブラウザ上のターミナル）と📜ログタブには「接続先の
  コンテナ」の選択欄があり、メインコンテナだけでなく各サイドカーにも
  個別に入って操作したり、ログを確認したりできます。

もっと複雑な構成（8個以上のコンテナ、追加のvolumeなど）が必要な場合は、
「YAML」サブタブで生のDeployment YAMLを直接編集することもできます。

#### 追加の公開ポート（VPNなどHTTPではないプロトコル向け）

「設定」タブの「追加の公開ポート」から、上記のFQDN/ポート（Traefik経由、
常に443番）とは別に、TCP/UDPのポートを直接追加できます。SoftEther VPNの
L2TP/IPsec（`500/udp`・`4500/udp`）のような、Traefikでは中継できない
HTTP以外のプロトコルを外部公開したい場合に使います。

> **Traefikを経由しません。** ここで追加したポートには、FQDNによる
> 絞り込みもTLS終端も一切かかりません。指定したポートは、このノードに
> 到達できる誰からでもそのままアクセス可能になります（ホストの
> ファイアウォール（ufw等）でも遮断できません — Traefik自体の80/443番と
> 同じ、k3sのklipper-lbによる直接のポート公開のためです）。信頼できる
> 用途にのみ使用してください。

- 「+ ポートを追加」で外部ポート番号（1〜65535）とプロトコル（TCP/UDP）を
  指定します。最大10個まで追加できます。
- 「転送先」ポートは任意です。空欄なら外部ポートと同じ番号でコンテナへ
  転送されます。コンテナが実際にリッスンしているポートが外部公開したい
  番号と異なる場合のみ入力してください（例: 外部からは`4500/udp`で
  受けつつ、コンテナ内部では`14500`で待ち受けさせたい場合）。
- 80番・443番は外部ポートとしては指定できません（Traefik自体が使用する
  ため）。転送先ポートには制限はありません。
- **同じ外部ポート番号+プロトコルの組み合わせは、他のContainerアプリと
  重複できません**（保存時にエラーになります）。Traefik経由のポートと
  違い、追加ポートはFQDN等で区別できない生のポートなので、複数アプリで
  同じ番号を共有することはできません。
- 追加/削除すると、コンテナのメインのServiceとは別に`<アプリ名>-raw`
  というLoadBalancer型のServiceが作成/削除されます。アプリを削除すると
  自動的に一緒に削除されます。
- インストール時に`SPINDECK_DUAL_STACK`を有効にしたノードでは、
  IPv6でも待ち受けます（Traefik自体の80/443番と同じ扱いです）。
  デュアルスタックでないノードではIPv4のみになります。

#### 🖥️ コンソール（ブラウザ上のターミナル）

既存アプリの編集画面には「🖥️ コンソール」タブがあり、`kubectl exec`相当の
インタラクティブなターミナルをブラウザから直接開けます。レプリカが複数ある
場合は、どのレプリカに接続するかも選べます。このコンテナが実際に実行して
いる内容そのものに対する、制限のないシェルアクセスです。

#### 📜 ログ

既存アプリの編集画面には「📜 ログ」タブもあり、`kubectl logs`相当の出力を
ブラウザからそのまま確認できます（直近500行、レプリカが複数ある場合は
Pod名のprefix付き）。「更新」ボタンで再取得します。

#### YAML編集（上級者向け）

「設定」タブの中の「YAML」サブタブから、DeploymentとServiceの生YAMLを
直接編集できます。env変数、複数コンテナ、独自のcommand指定など、上の
フォームには無い項目も自由に書けます。`metadata.name`/`metadata.namespace`
は保存時に自動的に上書きされますが、それ以外は基本的に制限がありません。
ただしホストへ抜け出せてしまう設定は拒否されます:
`privileged`・`allowPrivilegeEscalation`・`capabilities.add`、
`hostNetwork`/`hostPID`/`hostIPC`、コンソールが管理する1つのディレクトリ
以外への`hostPath`マウント、`automountServiceAccountToken`（常に無効化
されます）。

> **`spinapp-ui.dev/app`ラベルを消してしまうと、そのアプリが一覧・削除・
> 🖥️コンソール（exec）から認識できなくなります。** YAMLタブは常に今動いて
> いる実際のマニフェスト（新規作成時はフォームと同じ内容の雛形）から
> 始まるので、既存の値は残したまま必要な部分だけ編集することを
> おすすめします。

## アプリを守る（認証）

この節はNew App / New Site / New Proxy / New Containerが対象です
（New Cronはそもそも外部公開されません）。

作ったアプリを誰でもアクセスできる状態のままにしたくない場合、各アプリの
編集画面にある **🔒 認証** タブから、2種類の保護方法を選べます（併用は
できません、どちらか一方です）。

- **HTTP Basic認証** — ユーザー名とパスワードを1組設定するだけの、
  シンプルな保護です。ブラウザ標準のログインダイアログが出ます。
- **OIDC認証（許可ユーザーのみ）** — コンソール自体と同じKeycloakログインを
  再利用し、「このアプリを見て良いユーザー名」を一覧で指定します。
  ログインしていないユーザーはKeycloakのログイン画面に飛ばされます
  （コンソール自体がローカルアカウント方式の場合、この認証方式は
  利用できません — Keycloakを設定している場合のみ使えます）。

どちらにも保護しない場合、アプリは誰でもアクセスできる状態になります
（New Proxyで社内システムを中継する場合は特に注意してください）。

New Containerだけは、**「TLSの扱い」が「kubespin（Traefik）で終端」の
場合にのみ**認証を設定できます（「コンテナへパススルー」はTraefikが
中身を復号しないため、認証を挟めません）。専用ドメインは自由入力の
FQDNで構いません（`/config`への事前登録は不要です）が、OIDC認証を
使う場合はそのドメインに対して`https://<ドメイン>/_spindeck/oidc/callback`
をKeycloak側のクライアントのRedirect URIとして追加登録してください。

## 独自ドメイン（FQDN）で公開する

この節はNew App / New Site / New Proxyが対象です。デフォルトでは
これらのアプリは全て `https://<公開ホスト名>/<アプリ名>/` という共通の
ホスト名の下に公開されますが、アプリごとに専用のドメイン（例:
`myapp.example.com`）を割り当てることもできます。

1. `/config` の「アプリ専用ドメイン (FQDN)」セクションで、使いたいドメインを
   あらかじめ登録します。
2. 各アプリの編集画面で、Name欄の横のドロップダウンから登録済みドメインを
   選択します。
3. 選択すると、そのアプリはパス（`/アプリ名/`）だけでなく、指定した
   ドメインでのアクセスでしか反応しなくなります（パス自体は付いたままです）。

> ドメインを実際に使うには、そのドメインのDNSレコードがSpinDeckの
> サーバー（正確にはTraefikのIP）を指すよう、別途設定しておく必要が
> あります。

New Containerの専用ドメインはこれとは仕組みが異なります —
`/config`への事前登録は不要（自由入力）で、パスは付かずドメイン全体を
そのアプリが専有します。詳細は
[New Container（Dockerコンテナ）](#new-containerdockerコンテナ)を
参照してください。

## HTTPSで公開する

`/config` の「HTTPS」セクションから、SpinDeckが直接HTTPS(443番)で
待ち受けるように切り替えられます。

1. あらかじめ用意した証明書ファイル・秘密鍵ファイルを、サーバー上の
   固定パス（デフォルト `/etc/spinapp-ui/tls/cert.pem` /
   `/etc/spinapp-ui/tls/key.pem`）に配置します（証明書自体の取得・更新は
   SpinDeckの範囲外です — Let's Encrypt・社内CA・購入した証明書など、
   普段お使いの方法で用意してください）。
2. `/config`の「HTTPS」セクションで証明書が「設定済み」と表示されることを
   確認します。
3. 「HTTP (80番) で待ち受ける」/「HTTPS (443番) で待ち受ける」から選び、
   保存します。切り替えると、既存の全アプリのルーティング設定が自動的に
   再適用されます。「HTTPS」に切り替えると、80番ポートの外部公開も
   自動的に止まります（ホスト側のファイアウォール設定に関わらず、
   443番だけが外部から到達可能になります）。
4. 証明書ファイルを差し替えるだけで、数十秒以内に自動的に反映されます
   （再起動不要）。

管理画面（このコンソール自体）も同じ経路で公開したい場合は、同じ
「HTTPS」セクションのチェックボックスから有効にできます（既存の
`SPINAPP_UI_HOST_IP` の設定と、Keycloakの Redirect URI の設定が
必要です）。オフのままでも、`http://<サーバーのIP>:8080/` への直接
アクセスは引き続き使えます。

> New Containerの「TLSの扱い」で「kubespin（Traefik）で終端」を選んだ
> 場合は、この「HTTPS」セクションの設定にそのまま従います（HTTPのままなら
> 80番で、HTTPSに切り替えていれば443番で待ち受けます）。「コンテナへ
> パススルー」を選んだ場合は、この設定に関わらず常に443番ポートで
> 待ち受けます（コンテナ自身が証明書を扱うため）——このため既定では、
> HTTPモードのままでも443番は外部に公開されたままになります。
> パススルーモードを一切使わない場合は、`/config`の「New Containerの
> 『コンテナへパススルー』モードを許可する」チェックボックスを外すことで、
> HTTPモード中は443番も含めて完全に外部公開ポートが無くなるようにできます
> （既にパススルーモードのアプリがある場合は外せません）。

## コンソール自体を守る（ログイン方式・アクセス制限）

`/config` の「コンソールのログイン方式」セクションから、コンソール自体の
ログイン方式をいつでも切り替えられます（どちらか一方のみが有効です）:

- **ローカルアカウント** — デフォルトの方式です（インストール時に管理者
  アカウントが1つ自動作成されます）。外部のIDプロバイダを使わず、コンソール
  自身が保持するユーザー名/パスワードの組でログインします。同じ「ローカル
  アカウント管理」セクションから、複数のアカウントを登録・削除・
  パスワード変更できます。
- **Keycloak（OIDC）** — 設定したKeycloakのレルムでログインできる人なら
  誰でもコンソールにログインでき、全てのアプリを管理できます。

いずれの方式でも、アクセスできる人を絞りたい場合は次の方法があります:

- **Keycloakの場合**: `/config` の「コンソールへのアクセス制限」
  セクションから、ログインを許可するユーザー名の一覧を指定できます
  （一覧が空の場合は、Keycloakでログインできる人なら誰でも管理可能です）。
- **ローカルアカウントの場合**: そもそも登録したアカウントの分しか
  ログインできないため、「アクセス制限」の一覧は使われません。
  「ローカルアカウント管理」でアカウントを削除するだけで絞れます。

> どちらの方式でも、自分自身をロックアウトしてしまう操作（自分を含めない
> 保存、自分自身の削除、最後の1アカウントの削除、アカウントが0件の状態での
> ローカルアカウントへの切り替えなど）は保存時に拒否されます。

`/config` の「セッションのアイドルタイムアウト」セクションでは、ログイン後
どれだけ操作が無いとセッションが自動的に失効するかを分単位で設定できます
（デフォルト30分）。Keycloak・ローカルアカウント・アプリ個別OIDCログインの
いずれにも共通して適用され、操作を続けている間は延長され続けます
（＝固定の有効期限ではなく、アイドルタイムアウトです）。変更に再起動は
不要です。

## アクセス状況を見る（Analytics）

**📈 Analytics** から、直近のアクセス状況（リクエスト数の推移、エラー率、
応答時間、アプリごとのアクセス数、直近のアクセスログ）が確認できます。
別途監視ツールを用意する必要はありません。

期間選択の隣にあるドロップダウンで、特定のアプリだけに絞り込めます
（「全アプリ」で解除）。コンソール自体の内部エンドポイント
（`/_spindeck/*`、OIDC認証のforwardauth等）の通信は、登録したアプリでは
ないため、集計・絞り込みどちらからも自動的に除外されています。

ページ上部には、実際にどのログファイルを読んでいるか（パス・サイズ・
最終更新時刻）が常に表示されます。ファイルが見つからない、または
1時間以上更新されていない場合は警告が出ます — Traefik自体の書き込み先
設定とコンソールの読み込み先設定がズレている（片方だけ設定変更された
等）ときに気付けるようにするためのものです。

## 複数台構成（ピアレプリケーション）

複数台のSpinDeckノードを使って可用性を高めたい場合、`/config` の
「ピアノード」セクションから他のノードを登録できます。登録すると、
アプリの作成・編集・削除操作が自動的に他のノードにも反映されます。
各ノードはあくまで独立したクラスタのままで、Kubernetesクラスタ自体が
統合されるわけではありません。

## アプリのエクスポート・インポート

各アプリの編集画面右上（Container/JS/Site/Proxy/Cron Jobいずれも）にある
**⬇️ エクスポート** から、そのアプリ1件分の設定をJSONファイルとして
ダウンロードできます。ダッシュボードの **⬇️ 全体をエクスポート** からは、
登録されている全アプリをまとめて1つのJSONファイルにダウンロードできます。

エクスポートしたファイルは、サイドバーの **⬆️ Import** ページからアップロード
（またはJSONを直接貼り付け）することで、そのノードにアプリを作成・復元
できます。同名の既存アプリがある場合は、その場で設定が上書きされます。
用途としては、ノード再構築前のバックアップや、あるノードから別のノードへの
手動移行を想定しています。

インポートは実行したノードにのみ適用され、複数台構成（ピアレプリケーション）
していても他ノードへは自動連携されません。ノードごとに個別にインポートして
ください。

エクスポートファイルにはBasic認証のパスワードハッシュやOIDC許可ユーザーの
一覧など機微な情報がそのまま含まれます（インポート後すぐ動かせるようにする
ための意図的な仕様です）。ファイルの取り扱いには注意してください。

## バックアップ（`backup.sh`）

このリポジトリのチェックアウトで`sudo ./scripts/backup.sh`を実行すると、以下を
1つの`tar.gz`にまとめて`/data/backup/`へ保存します。

- Containerアプリの永続ストレージの実データ（例: DBのファイル。設定
  だけでは復元できない部分です）と、Siteアプリのファイル本体（こちらは
  下記`apps-export.json`にも同じ内容が含まれる、念のための二重保存）。
  `/data`をまるごとではなく、実際に使われているデータ用ディレクトリ
  だけを対象にしています（k3s自体のデータストア・ローカルレジストリの
  イメージ・Traefikのログ・`lost+found`など、`/data`にはSpinDeckの
  実データ以外もいろいろ置かれがちで、それらはどれも新しいノードで
  `install.sh`を実行すれば作り直されるため対象外です）。
- 登録されている全アプリの設定（`apps-export.json`）—— 上記「アプリの
  エクスポート・インポート」の**⬇️ 全体をエクスポート**と全く同じ内容
  （Container/JS/Site/Proxy/Cron Jobすべて、Siteアプリの実ファイル内容や
  各種パスワードハッシュも含む）。コンソールへのログインなしでcron等
  から実行できるよう、HTTPを介さず直接生成しています。
- `/opt/spinapp-ui/config.json`（登録FQDN・ピア一覧・SMTP・コンソール
  ログインアカウント・レジストリ認証情報など、`/config`の設定一式）と
  `/etc/spinapp-ui/env`（OIDC設定・ピアトークン・ホストIPなど）——
  別ノードをこのノードの「後継」としてすぐ使えるようにするためのものです。

パスワード・トークン類が平文で含まれるため、アーカイブ自体を
`chmod 600`にしています。取り扱いには注意してください。

**復元方法**: `tar.gz`を展開し、(1)`containers/<アプリ名>/`以下を新しい
ノードの`/data/containers/<アプリ名>/`へ配置、(2)`config.json`/`env`を
それぞれ新ノードの`/opt/spinapp-ui/config.json`/`/etc/spinapp-ui/env`
に上書きしてから`spinapp-ui`を再起動、(3)`apps-export.json`をサイドバーの
**⬆️ Import**ページへアップロード、の3ステップです。`env`内の
`SPINAPP_UI_HOST_IP`だけは元のノード固有のLAN IPが入っているため、
新しいノードの実際のIPアドレスに書き換えてください（それ以外の値は
そのまま使えます）。

## 動作確認（`healthcheck.sh`）

`sudo ./scripts/healthcheck.sh`を実行すると、Container/JS/Site/Proxy/Cron Job
の全アプリ種別を`zzzhealthcheck-`という使い捨ての名前で実際に作成し、
Traefik経由の実際のHTTPアクセスまで含めて動作確認したうえで、
テスト終了時に全て削除します（既存の登録済みアプリには一切触れません）。
あわせて、これまでに実際に起きた回帰（CPUオーバーコミット、
Deploymentのロールアウト方式、追加ポートのホストポート衝突対策、
Proxyアプリのバックエンド検証境界など）も個別に再確認します。
`upgrade.sh`実行後に流すことを想定していますが、いつ実行しても
安全です。最後に合格/不合格件数のサマリーが表示され、何か1つでも
失敗があれば終了コードが1になります（cron等での自動実行にも使えます）。

## 困ったときは

- **ログインできない / OIDCエラーになる** — Keycloakの設定
  （Issuer・Client ID・Client Secret・Redirect URI）を管理者に確認して
  もらってください（ローカルアカウント方式の場合は、ユーザー名/パスワードが
  `/config`の「ローカルアカウント管理」に登録されているか確認してもらって
  ください）。
- **OIDC認証のログインが遅い・ずっと読み込み中になる** — Keycloakへログイン
  情報を送信した後（画面がKeycloakからアプリに戻ってくるタイミング）で
  止まる・遅い場合、コンソールを動かしているサーバーからKeycloakへの
  ネットワーク疎通に問題がある可能性があります。特に、Keycloakのホスト名が
  IPv4/IPv6の両方のアドレスを持つ場合、IPv6経路だけが不通（設定はあるが
  実際には応答が返ってこない状態）だと、IPv6を試してから諦めてIPv4に
  切り替わるまでの待ち時間が発生することがあります。管理者に、コンソールの
  サーバー上で`curl -6`/`curl -4`それぞれでKeycloakへ疎通確認してもらって
  ください。
- **アプリがデプロイに失敗する** — 各アプリの編集画面の「ログ」タブに
  ビルドログが出ます。JavaScriptの構文エラーなど、大抵はここで原因が
  分かります（New Containerの「📜 ログ」タブは`kubectl logs`相当の
  実行時ログで、ビルドログではありません。起動直後にコンテナが
  クラッシュしている場合の原因確認に使ってください）。
- **404になる** — デプロイが完了しているか（保存ボタンを押した後、少し
  時間を置く）、URLのパス（`/アプリ名/` の末尾スラッシュなど）を確認して
  ください。
- **New Containerが一覧・削除・🖥️コンソールから見えなくなった** —
  YAMLタブで`spinapp-ui.dev/app`ラベルを書き換えてしまった可能性があります。
  `kubectl get deployment -A -l spinapp-ui.dev/app`で実際のラベルを
  確認し、YAMLを修正して保存し直してください。
- **New Containerの🖥️コンソールに繋がらない** — コンテナ側にシェル
  （`bash`または`sh`）が入っていないイメージ（distroless等）だと接続しても
  エラーが表示されるだけになります。
- **それでも分からない** — サーバーにログインできる方は
  `kubectl get pods -A`（全体の状態確認）、
  `systemctl status spinapp-ui`（コンソール自体の状態確認）を確認して
  ください。

## 用語集

SpinDeckの裏側の仕組みに出てくる単語です。使う上で必須の知識ではありません
が、エラーメッセージなどに出てきたときの手がかりにしてください。

- **Kubernetes（k8s）** — 複数のアプリをまとめて管理・実行するための基盤
  ソフトウェア。SpinDeckはこの上で動いています。
- **k3s** — Kubernetesの軽量版。1台のサーバーでも手軽に動かせます。
  SpinDeckはこれを使っています。
- **Wasm（WebAssembly）** — アプリを高速・安全に実行するための軽量な
  実行形式。New App/Site/Proxy/Cronは、裏側でこの形式にビルドされて
  実行されます（New Containerだけは対象外で、通常のDockerコンテナとして
  動きます）。
- **SpinKube / Spin** — WasmアプリをKubernetes上で動かすための仕組み。
  SpinDeckが裏側で使っています。
- **Deployment** — Kubernetesの「指定した数のコンテナを動かし続ける」
  という基本的な仕組み。New Containerはこれとして動きます。
- **Traefik** — SpinDeckの手前でリクエストを各アプリへ振り分ける
  役割（リバースプロキシ）を担うソフトウェアです。
- **Keycloak / OIDC** — ログイン・認証を担う仕組みの1つです。SpinDeck
  自体は自前のパスワード管理を持たず、Keycloakのようなこの仕組みに
  乗っかるか、コンソール内蔵のローカルアカウント（ユーザー名/パスワード）を
  使うかを選べます。
- **CronJob** — Kubernetesの「定期実行」の仕組み。New Cronで作った
  ジョブはこれとして動きます。
